Harbourline Studio

harbourline.example · no-code marketing site + hosted course platform · no custom auth, no database of our own
Demo report. Harbourline Studio is a fictional application invented for this example. The findings are written the way real ones read, but no real product was audited to produce this page.
CheckVerdictEvidence
1 · Forces HTTPSRedirect + HSTS PLATFORM Both hosts terminate TLS and redirect. Probed each: marketing domain 301 → https, course subdomain 301 → https. HSTS present on the course platform, absent on the marketing site, which is not configurable on this plan.
2 · Passwords hashedOr managed auth PLATFORM No custom auth exists. Student accounts live entirely in the course platform, which handles credentials. Nothing in this stack stores a password, so there is no second path to check.
3 · Bot protectionEvery public POST PARTIAL Three public forms. CAPTCHA is on for the two lead forms — verified in the form builder settings, one screenshot each. The newsletter embed on /blog has it switched off, and that form has taken 1,900 submissions in 30 days against 40 confirmed subscribers, which is what a bot-filled list looks like.
4 · Sessions expireFinite TTL + rotation PLATFORM Course platform session settings read directly: 30-day session, "remember me" 90 days. Long for the format, but bounded and platform-managed. No custom session layer exists.
5 · CSRF protectionTokens or SameSite PLATFORM All state changes happen inside the two vendors’ own applications. There is no custom endpoint in this stack that changes state, so there is nothing here to protect or to get wrong.
6 · Reset links one-timeTTL ≤ 1h, consumed UNKNOWN The reset flow is vendor-managed and neither the expiry nor the single-use behaviour is exposed in the admin settings or documented. Requested confirmation from vendor support; until an answer arrives this is UNKNOWN and scores 0. It is not assumed safe.
7 · Scoped DB keyAnon in browser only PASS No database of our own. But the tracking snippet in the site-wide header was reviewed and the published pages were swept for key-shaped strings — the realistic leak path on a no-code stack is a credential pasted into a custom code block. Nothing found across 24 pages.
8 · Clean logsNo credentials logged PLATFORM No application logs of our own. Two automations forward form submissions to a third-party inbox; both were reviewed and neither carries a credential field.
9 · Billing alertsCap on every backend PARTIAL Both platform subscriptions are flat-rate, so they cannot surprise anyone. The email-sending automation is metered per action and has no cap — and it is fed by the unprotected newsletter form from check 3, which is how the two findings compound.
10 · Automated backupsRan, retained, restorable PARTIAL Both vendors back up their own infrastructure, which protects them and not necessarily you. A manual student-and-order export was last taken 2026-05-02, three months ago, and there is no schedule. If access to the account were lost tomorrow, three months of records go with it.
Scored with securitymaxx — 10 checks, evidence required. PASS counts 1, PARTIAL 0.5, everything else 0. An item that could not be verified is UNKNOWN and scores zero, so the number is a floor rather than an estimate.
Read-only audit: source and config were read, and live probes were ordinary HTTP requests. Nothing was exploited and nothing was written to. Secret values are redacted to file and line — these reports get forwarded.
